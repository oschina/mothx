## 0. 总体结论

这批提交解决的是两个真实且严重的问题——**绑定失败时 Runtime 与适配器停留在不同会话上**(半初始化会话 + 调用方以为失败),以及**一次被中断的写入让 `sessions.db` 永久无法启动**——并且都以"提交前先准备、只在成功后原子发布"的正确形态落地,没有在适配器里打补丁。TUI 的 `activateSession` 与 Runtime 的 `BindSession` 保持了同一时序,两侧都补了失败路径断言。

需要修的问题集中在**新命令 `mothx pure` 的边界与错误路径**:它在"最坏失败路径"上把恢复线索丢掉了(F1),在"只剩 sidecar"这一恰好属于它自己职责范围的场景下失效(F2),并且只重置数据库行而把同一目录下的 Runtime 资源树留成无法寻址的孤儿(F3)。`internal/db` 的索引修复则存在锁争用被误报为损坏(F4)与修复过程完全静默(F5)两点。

## 1. 逐项发现与修复方向

### F1 [高] `mothx pure` 在新建失败路径上丢弃备份位置,把用户引向错误结论

- **位置**: `cmd/mothx/main_pure.go:31-36`;`internal/session/database_reset.go:55-60`
- **现象**: `ResetDatabase` 特意在"移动已成功、但 `OpenRootDB` 新建失败"时把 `backupPath` 与 error 一起返回(注释与实现都表明这是"数据已移走、需要告知去向"的那条路径)。命令层 `backup, err := session.ResetDatabase(dir)` 后立即 `if err != nil { return fmt.Errorf("reset sessions database in %s (stop every other mothx process using this directory and retry): %w", dir, err) }`,把 `backup` 丢了。
- **影响**: 此刻用户的库**已经安全地躺在同目录的 `sessions.db.pure-<ts>.bak` 里**,而唯一的人类可见输出是"重置失败,请先停掉其他 mothx 进程再重试"。用户会按提示重跑(再次移动→留下第二个 bak),或在相信数据已丢失的前提下继续操作。这是 `c38f2ea8` 想解决的"错误信息不足"问题的同一类,但发生在更危险的那条分支上。
- **修复方向(未改代码,仅建议)**: `backup != ""` 时把该路径拼进返回错误(例如 "previous database was moved to %s; nothing was lost"),并考虑在 `c38f2ea8` 新增的失败用例旁补一条"移动成功 + 新建失败必须报告 bak 路径"的断言。

### F2 [高] 只剩 `-wal`/`-shm`/`-journal` 而没有主库文件时,sidecar 既不被归档也不被报告

- **位置**: `internal/session/database_reset.go:39-53`(`ErrNotExist` 分支 49-50 行:`// Nothing to move; the database created below is the first one.`)
- **复现**: 在空目录内先写入 `sessions.db-wal`,再执行 `go run ./cmd/mothx pure --session-dir <该目录>`。输出只有 "Created a fresh sessions database",**没有归档提示**;执行后目录里只剩新建的 `sessions.db`,预先放置的 `-wal` 已被 SQLite 静默处置掉(不是被本命令归档)。
- **根因**: 移动动作只在 `os.Stat(dbPath)` 成功时发生,sidecar 的遍历(`moveDatabaseFiles`)完全挂在主文件存在这一前提上。而"主库缺失、sidecar 残留"正是该命令的立项理由("手动删库容易出错:残留的 `-wal`/`-shm` 会被下一个数据库继承",见 `df360506` 提交说明与 `docs/*/cli-reference.md`)所描述的危害场景之一,恰好落在实现覆盖范围之外。
- **影响**: 新建库能否干净启动取决于 SQLite 对残留 WAL/journal 头的内部处置(无效头被忽略并覆盖、看似有效的头会触发恢复尝试并可能报 `SQLITE_NOTADB`/"database disk image is malformed"),即把产品承诺交给了引擎实现细节;同时"什么都没归档"的输出与真实发生的文件消失互相矛盾,没有任何恢复线索。
- **修复方向**: `ErrNotExist` 分支同样枚举 `databaseSidecarSuffixes`,把存在的 sidecar 移到 `resetBackupPath` 生成的备份名下并在输出中报告;或检测到"有 sidecar 无主库"时显式拒绝并提示原因。两种都比依赖 SQLite 处置更符合该命令自己的契约。

### F3 [中] 只重置规范数据库,同目录 Runtime 资源树成为不可寻址孤儿

- **位置**: `internal/session/database_reset.go`(整体设计);`cmd/mothx/main_pure.go:22-24` 命令自述
- **实测本机 `~/.mothx/sessions` 规模**: `sessions.db` 189M + `-wal` 4.0M,同级 `artifacts/` 106M、`channels/` 1.6M、`knowledge-bases/` 168K。
- **问题**: 附件/产物字节在 `sessionDir/artifacts/` 下，而其规范记录（归属、过期时间）在 `sessions.db` 里。重置后行没了、字节还在：附件/产物再也无法被列出或清理（其保留期由数据库记录驱动，见 AGENTS.md "attachment/artifact lifecycle" 条目）。命令自述是"starts a brand-new empty one"，对磁盘侧只字未提。
- **勘误（2026-09-18 第四轮复核后修正，详见附五）**: 本条初稿曾把 `channels/` 与 `knowledge-bases/` 一并归为"记录在 sessions.db、重置后失去引用"的同性质孤儿。该判断**错了**：`channels/` 是自带 `sessions.db` 的独立会话根，`knowledge-bases/<id>.db` 自身就是该库的权威存储（配置行在里面，枚举靠扫目录）。真正因重置而不可寻址的只有 `artifacts/`，而后续三轮的回收实现恰好只覆盖这一类，结论与代码未受影响。
- **修复方向**: 至少把这三个目录连同其大小写实地打印出来并写入 `docs/{en,zh}/cli-reference.md`;若要与"nothing is deleted"的承诺一致,则把它们一并改名归档(或提供 `--with-resources` 之类的显式开关)。注意不要顺手删源目录,知识库源目录按 AGENTS.md 属只读、且其删除规则独立于本命令。

### F4 [中] `checkIntegrity` 把 `REINDEX` 的锁争用/只读失败当成损坏来中止启动

- **位置**: `internal/db/db.go:276-300`(`REINDEX` 在 288 行);对照既有护栏 `internal/db/db.go:221` `unrebuildableReason`、`internal/db/busy.go:45` `isSQLiteBusy`、`internal/db/recovery.go:293` `isSQLiteReadOnly`
- **场景**: 两个 `mothx` 进程几乎同时启动(或另一进程持写锁)时,先通过检测的一方执行 `REINDEX` 会返回 `SQLITE_BUSY`,于是启动失败,错误文案是 "repair SQLite indexes after integrity check %q: database is locked"——把一次纯可用性故障描述成"修复失败/疑似损坏",且与 `c0f48792` 自身"仅限那一类精确 quick_check 结果可修,其余一律中止"的意图相反。同一文件里,重建路径已经明确拒绝用 busy/read-only 推断损坏。
- **影响面**: 该包的 `TestRebuildGuardrailsSkipTransientFailures` 已经为重建方向钉死了这类混淆(`recovery_test.go:251`),说明这是项目既定纪律,而新的修复路径未纳入。
- **修复方向**: 用现成的 `isSQLiteBusy`/`isSQLiteReadOnly` 分类 `REINDEX` 错误——busy 走一次有界重试(预算可复用 `internal/db/db.go:352` 的 `BusyTimeout = 10s`,与租约心跳同一口径),仍失败则返回"另一进程持有 SQLite 写锁,索引修复未执行"而非损坏类错误;read-only 单独成句。与 AGENTS.md "transient failure is an availability problem, never ownership loss" 的取向一致。
- **同一分支的正向确认**: `PRAGMA quick_check` 多行输出时 `QueryRow` 只取第一行(`quickCheck`,301 行)是可接受的——修复后无条件复检(`integrity != "ok"` 即中止),因此"索引问题 + 表页损坏"并存时仍会中止,不会漏放。

### F5 [中] 索引修复全程静默,用户永远不知道库曾受损

- **位置**: `internal/db/db.go:276-300`。全包仅有一处日志——`internal/db/recovery.go:123` 的 `log.Printf("[db] %s", recovery.Describe())`,且只覆盖迁移重建;新增的索引修复路径无对应输出。
- **对比**: 迁移重建除了 `log.Printf`,还走 `recordMigrationRecovery` → `TakeMigrationRecoveries`,并经 advisory bus 广播对端事件,前端"恰好一次"告知用户去向(`internal/session/database.go` 的 `TakeDatabaseRecoveries` 注释即为此约定)。一次成功自愈的 `REINDEX` 两者都没有。
- **影响**: 单进程场景可接受,但真实用户同时开着 TUI、`serve`、Desktop(多个 `mothx acp` 子进程)时,"上一次会话莫名中断/这次启动做了底层修复"这类信息缺失会让排查无从下手。
- **修复方向**: 至少补一行与 `recovery.go:123` 同风格的 `log.Printf("[db] ...")`;更好是新增一类一次性上报(如 `IndexRepairReport{Path, Index, At}`),复用现有 `SetMigrationRecoveryNotifier`/`Take...Recoveries` 通道或在其旁并列,由 TUI/serve/Desktop 在会话里提示一次。

### F6 [低/DRY] Runtime 内部出现两份"发布"和两份"准备"逻辑,存在漂移风险(当前无行为差异)

- **位置**:
  - 发布重复: `internal/agentruntime/session_runtime.go:288-301`(`BindSession` 内联)vs `internal/agentruntime/expert.go:372-394`(`publishPreparedExpertResources`)
  - 准备重复: `internal/agentruntime/expert.go:332-365`(`prepareBoundSessionResources`)vs `expert.go:286-325`(`prepareExpertResources`)
- **现状**: 两处发布当前字段一致(`BindSession` 额外只做 `ExpertCenter` 与身份字段);两处准备的差异只在 bundle 来源(持久化绑定 vs 显式 expertID)。`RefreshResources` 里的 `r.WorkDir != workDir || r.Manager != manager` 竞态检查(`session_runtime.go:1113-1115`)在新路径下不再需要(整体在同一把写锁内完成),这一点是净改善。
- **风险**: 以后给 `preparedExpertResources` 加一个字段(或新增一项需要同步的工具,如 core tools 之外的注册),极易只改一处。AGENTS.md 的"one owner each"精神在此处应体现为一个实现而非两份平行副本。
- **修复方向**: 抽出 `publishPreparedExpertResourcesLocked(prepared)`(要求调用方持锁)供两处复用;准备的公共尾段抽成 `buildPreparedResources(bundle)`。属纯重构,不改行为。

### F7 [低] TUI 仍有一处 `cwd` 双写,削弱"提交由 `activateSession` 独占"的新不变量

- **位置**: `internal/tui/commands_session.go:359`(`activateSession(newSess)` 之后仍 `a.cwd = newSess.GetHeader().Cwd`)
- **说明**: `activateSession`(`internal/tui/input.go:673-687`)只在 `Cwd != ""` 时提交 `a.cwd`;`switchToSession` 随后又无条件赋值(空值也会写入)。当前行为等价于修复前,但"成功激活之后才提交适配器状态"这一约定只剩一半。
- **修复方向**: 删除该行;若确实需要"空 Cwd 也要覆盖"的语义,则把它移进 `activateSession` 并统一两条路径。

### F8 [低/产品护栏] `pure` 无确认、无在线对端预检,仅靠帮助文本承担并发安全

- **位置**: `cmd/mothx/main_pure.go:22-24`(提示"先停掉其他进程")、`internal/session/database_reset.go:23-25`(注释承认"本进程无法检测")
- **说明**: 该命令会清空可见会话历史(数据保留在 bak 中,但用户视角等同删除),却对目标目录是否有活跃对端毫无检查;`c38f2ea8` 的补救是把 Windows 的 `Access is denied` 文案化,本质是事后归因。
- **可用素材**: `session_runtime_leases`(`owner`/`epoch`/`token` fenced CAS)与 `internal/db` 的 advisory bus 已能表征"有别的进程正在使用该会话目录";`d06922a5` 之后租约语义也稳定。
- **修复方向**: 重置前读一次该目录的租约/对端公告,存在活跃持有时默认拒绝并列出持有者,`--force` 才继续;或把"未发现活跃对端"作为提示打印出来。这样跨平台一致,而不是只在 Windows 上靠改名失败暴露。

### F9 [低/测试卫生] 回滚与新路径缺少针对性用例;`rollbackDatabaseMove` 的恢复顺序可再收紧

- **缺测清单**(与 F1/F2/F4 一一对应):
  1. 只有 sidecar、没有主库的目录(F2 的场景,`internal/session/database_reset_test.go` 现有两用例都假定了主库存在或目录完全干净);
  2. `moveDatabaseFiles` 中 sidecar 改名失败 → 整体回滚的分支(`database_reset.go:88-100`,当前零覆盖);
  3. `resetBackupPath` 的候选名冲突/有界重试(`database_reset.go:104-121`);
  4. 非"wrong # of entries in index"类完整性失败仍中止启动(`internal/db/recovery_test.go:170` 只覆盖了修复成功路径);
  5. F1 的"移动成功但新建失败"必须把 bak 路径带回给用户。
- **顺序建议**: `rollbackDatabaseMove` 目前先恢复已移走的 sidecar、最后恢复主库(`database_reset.go:90-98`)。若在两步之间进程被杀,会留下"`sessions.db` 不存在但其 `-wal` 存在"的窗口——正是 F2 描述的状态。建议反向:先恢复主库文件,再恢复 sidecar。
- **可取之处**: `TestOpenRepairsStaleSecondaryIndex`(`recovery_test.go:170`)通过手工改写索引叶子页键值来制造"仅索引过期"的条件,不依赖任何测试钩子,是这种不可注入路径的好写法;`session_runtime_bind_test.go`/`session_activation_test.go` 都断言了失败后旧身份未被改动,正面覆盖了本批次的核心不变量。

## 2. 站得住的部分(复核确认成立)

- **提交顺序修复的形态正确**: 锁外 preflight(`NewInputMaterializer`/`NewAttachmentService`/`prepareBoundSessionResources`)→ 一次 `r.mu.Lock()` 内原子发布 → 失败即完全不改状态;`ensureOpen()` 仍在入口。旧路径把身份先写入、再靠 `rehydrateBoundResources()` 补救,失败即半初始化,新路径消除了这一类。
- **无条件替换 `r.Attachments`/`r.Inputs` 是安全的,且顺带修掉一个未被记录的潜在 bug**: 两个构造器都只校验参数、不触文件系统(`internal/agentruntime/input.go:104-116`、`input_materializer.go:141-157`),`AttachmentService` 仅 `{sessionDir, policy}` 无内存态,且全树五个生产调用点(`acp.go:1795`、`attach.go:68`、`session_runtime.go:268/988`、`delivery_recovery.go:163`)一律使用 `DefaultAttachmentPolicy()`——不存在"适配器注入自定义策略被覆盖"的可能。相反,原先的 `if r.Attachments == nil` 守卫意味着**复用中的 Runtime 在切换会话后仍指向第一个会话的附件目录**:受影响的是"一个 Runtime 多次 `BindSession`"的路径,即 TUI(`a.runtime` 全程唯一,`ensureRuntime` 只在为空时创建,切会话走 `runtime.go:71` 的 `BindSession`)以及 CLI 的 `sharedRuntimes` 复用路径——但后者更值得单独记录: `cmd/mothx/main_util.go:120-131` 在命中 `sharedRuntimes[0]` 时**根本不再调 `BindSession`**(只有新建 Runtime 分支才绑),即复用会话时连身份都不重绑;属与本批次同类的边界问题,但不属本批次引入。serve/ACP 每会话一个 Runtime,不受影响。建议为这一点单独补一句 changelog,因为它是当前说明未声称的用户可见行为。
- **TUI 侧时序与 Runtime 一致**: `activateSession` 把"决策恢复 → Runtime 绑定 → 提交适配器状态"排成一条线,`ensureSession` 与 `switchToSession` 两条入口共用,不再各写一遍 `a.session`。
- **文档同步完整**: `docs/{en,zh}/changelog.md` 与 `docs/changelog_online_{en,zh}.md` 四条(1 新特性 + 2 修复 + 交叉引用)均已同步,`docs/{en,zh}/cli-reference.md` 各 +23 行含 `--session-dir` 表与警示语。
- **`REINDEX` 作用域收得足够窄**: 只匹配小写化的 `wrong # of entries in index`,其余完整性失败一律中止;修复后复检,不做任何"看起来像坏了吗试试"的宽松处理,与"索引内容由表行派生、重建无损"的论证一致。
- **守卫与并发纪律未受影响**: `go test ./internal/architecture/...` PASS,未新增豁免;`BindSession` 的持锁段只含内存赋值,未把 `LoadContextResourcesWithExpert`(可耗时磁盘扫描)挪进锁内。

# 附二: F3 根因的独立修复——无引用附件存储回收（2026-09-18 第二轮）

## 1. 问题重新定义

第一轮把 F3 处理成"`pure` 要诚实报告它没归档什么"。复核后确认那只是症状：真正缺失的是一条**目录驱动**的回收路径。现状是

- 唯一删除附件字节的地方是 `AttachmentService.CleanupExpired`，它先查 `session_attachments` 中已过期的行，再删对应文件；调用点只有 `acceptArtifact` 开头那次尽力而为的清理。
- 因此"行已经不在了"的一切残留都永久不可回收，且有三条独立产生路径：
  1. `mothx pure` 归档数据库（行随库离开）；
  2. **删除会话**：`SessionDAO.DeleteSession` 会级联清掉 `session_attachments` 行，但没有任何地方删除其内容文件；
  3. **intake 失败**：`acceptArtifact` 先建 `artifacts/<id>/`、写 `.incoming-*`、rename 成 `content`，之后才插行；插行失败只 `os.Remove(finalPath)`，目录本身留下。
- 附带结论：过期清理本身也是"惰性搭车"的——只有新附件进来时才会跑一次；一个不再上传的实例永远不会回收任何东西。

## 2. 方案与护栏

新增 `internal/agentruntime/storage_reconcile.go`：`ReconcileArtifactStorage(ctx, sessionDir, policy, now)`，由 Runtime 独占目录侧回收，其他层只能调用与渲染。安全边界按"宁可漏删"排列：

1. **年龄下限** `now - (Retention + 24h)`（默认 8 天）。这是整套设计成立的关键：保留期定义的是"被引用的对象保证存活多久"，因此既无行引用、又已超过保留期+缓冲的字节，即使把归档数据库放回去也早已过期，删它不可能破坏可恢复性——也覆盖了 `pure` 之后立刻清扫会误删的情况（那时目录都是"新"的）。
2. **fail-closed**：`sessions.db` 不存在或读不出引用集时直接返回错误，删除数为 0。空引用集与"数据库打不开"在目录侧不可区分，所以后者绝不允许被当成前者。
3. **只认自己的形状**：目录名必须是 `acceptArtifact` 生成的 16 位小写 hex；内容只允许 `content` 或 `.incoming-*` 常规文件；出现子目录、其他文件名、符号链接、或顶层就是文件 → 计入 `SkippedUnrecognized`，不删。软链接一律不跟随。
4. **引用集同时看 `id` 与 `storage_key`**：两者不一致（历史/手工键值）时取并集保护，键值异常绝不会变成删除理由。
5. 结果计数显式化（`Scanned/Removed/Freed/SkippedReferenced/SkippedYoung/SkippedUnrecognized/AgeFloor`），"存储本来就干净"与"全都太新"可区分。

两个入口共用同一实现（不改 `CleanupExpired` 的行语义）：

- `acceptArtifact` 里紧跟过期清理之后调用 `reconcileArtifactStorageOpportunistic`，用 `atomic.Int64` + `Swap` 保证每进程每小时至多一次；错误被吞掉，回收失败永远不影响新附件。持锁检查：引用集读取走只读、无事务，目录遍历期间不持有写事务，intake 自身的写入顺序不变。
- `mothx pure --prune-unreferenced` 显式按需执行一次并打印回收量/因太新保留数/未识别条目数。`pure` 的默认行为仍是"什么都不删"。

# 附三: 第三轮——把回收接上共享 cron（2026-09-18）

## 1. 依赖方向决定了落点（先记录，避免下一个人重踩）

两个关键设计判断：

1. **派发点选在调度器内部而不是适配器 JobHandler**：`JobHandler` 允许 `handled=false` 表示"我不接，交给普通 agent 路径"。维护任务如果被某个适配器 decline，就会把它的 `prompt` 当成模型轮次去执行——这在语义上是危险的。所以在 `executeJobContext` 里对命名空间强制认领，且 `RunMaintenanceCronJob` 对**命名空间内任何未知 ID** 都返回 `handled=true + error`（记为 failed，绝不落到 agent）。
2. **投影只创建、不覆盖**：已存在的维护任务原样保留，因此运维者通过 store/API 把它 disable 就是一直 disabled；被删除则下次调度器启动自愈重建。任务 `SessionID` 为空，因此天然不进入任何 session 作用域列表；再叠加投影层过滤，`/api/cron`（无 sessionId 的全局列表）与 `mothx/manage/cron/list` 也不会把它当作用户自动化任务渲染——Desktop `CronPanel.tsx` 与 Web UI `Cron.svelte` 因此不会显示一条用户没建过、提示词是占位说明、还允许删除的假任务。显式按 ID 操作仍然可用，ID 已写入文档，保留为运维者的手动关闭口。

覆盖面：`mothx --cron`（CLI/TUI）、`mothx serve`、`mothx acp`（含 Desktop）三条路径都在 `Scheduler.Start()` 上拿到该任务；纯一次性 CLI 调用与未开 cron 的 TUI 仍由"intake 机会式清扫 + `mothx pure --prune-unreferenced`"兜底。

## 3. 过程中的反证（值得保留）

第一版直接把维护任务放进共享 store 后，`internal/acp` 的进程级契约测试 `TestACPStdioProcessManageCronRunCompletionAndStats` 立刻变红——它断言 `mothx/manage/cron/list` 初始为空，随后又按 `jobs[0]` 取用户任务。这说明"隐藏"不是洁癖而是既有契约：管理面契约测试与两个前端都在依赖"列表里只有用户任务"。按 `len(jobs)` 下标取任务的写法本身也偏脆（同名/新增系统任务都会打乱顺序），过滤恢复了对方的前提，同时保留了对方的断言强度。

# 附四: 第四轮——维护任务的可配置开关（2026-09-18）

## 1. 顺带解决附三遗留 1 与 2

原以为需要两件事（settings 开关 + "用户删除即停用"的持久标记），设计后发现开关本身就消除了第二件：**持久意图只存在 `settings.json` 里，store 中的 job 行只是投影**。于是"被删了怎么办"有了确定答案——下次调度器启动按策略重建；"想永久停用怎么办"也不再靠删除行表达，而是 `maintenance.reclaimAttachmentStorage=false`。不新增表、不新增列，也不需要靠命名空间猜意图。

## 2. 依赖与解析

`internal/cron → internal/agentruntime → internal/config` 的既有方向保持不变，因此：

- `internal/config`：新增可选 `maintenance` 对象（`reclaimAttachmentStorage *bool`，nil/true = 开，沿用 `updateCheck` 的默认-开惯例；`storageReconcileSchedule string`）。零值 `Settings{}` 不会序列化该段（指针 + omitempty），老配置文件行为不变。
- `internal/agentruntime`：`MaintenancePolicy{ReclaimAttachmentStorage, StorageReconcileSchedule}` + `DefaultMaintenancePolicy()` + `MaintenancePolicyFromSettings(*config.Settings)`，策略只在此处解析一次；`RunMaintenanceCronJob` 新增 policy 入参，关闭时返回"已跳过"而不是执行回收。
- `internal/cron`：`Scheduler.SetMaintenancePolicy`（未设置即用 Runtime 默认）、`ensureMaintenanceJob` 按策略收敛——开则保证存在并把 schedule 追平，关则删除自己那一行；schedule 校验仍留在拥有语法的一方（`NormalizeJobSchedule`），非法值记 `[cron]` 日志后回退默认，避免在 config 里长出第二个解析器。
- 三处适配器各加一行：`cmd/mothx`（`--cron`）、`internal/serve`（两处调度器构造 + `cronMaintenancePolicy()` 读取全局 settings）、`internal/acp`（`ensureManageCron`）。

两个刻意的取舍：

1. **改频率只改 schedule**：`RunCount`/`LastStatus`/`LastRun`/`CreatedAt`/`Enabled` 一律保留，因此不会因为编辑配置丢历史，也不会把用户暂停的任务偷偷启回来（附二 §2 的"只创建、不覆盖"原则保留下来）。
2. **关闭在下次调度器启动生效，但执行路径也校验策略**：serve 改配置会重启 cron 调度器（`applyConfigUpdate` 路径），所以实际收敛很快；而"旧进程留下的行仍然触发"这种窗口，由 `RunMaintenanceCronJob` 内的策略检查兜住，既不删数据也不报错。

# 附五: 勘误——`channels/` 与 `knowledge-bases/` 不是"重置孤儿"（2026-09-18）

## 1. 被推翻的结论

第一轮 F3 与附二 §5、附三 §5 曾把这两个目录与 `artifacts/` 并列为同一类问题（"规范记录在 sessions.db，重置后失去引用、永久占盘"），并建议"需要各自的持有者协议、留待后续"。用户追问概念时复核代码，结论反了：**它们根本不是重置造成的残留**，更不需要回收协议。

## 2. 证据

- `knowledge-bases/<id>.db` **自身就是权威**：`internal/session/knowledge_bases.go:153-179` 的 `ListKnowledgeBases` 先用 `listKnowledgeBaseDatabaseIDs`（`internal/session/knowledge_database.go:121-143`）**扫目录**得到有哪些库，再进每个文件读它自己的 `knowledge_bases` 配置行；`internal/session/schema.go` 里今天没有任何列引用知识库 ID，根库里那张 `knowledge_bases` 是旧布局，由 `knowledge_bases.go:742` 的 `migrateLegacyKnowledgeBaseStorage` 迁出。所以重置共享库不会让任何知识库失效。
- 它自己的删除路径正好演示了"持有者协议"的必要性：`knowledge_database.go:149-162` 先 `database.Close(path)`（撤掉 `internal/db` 按路径缓存的连接）再删 `.db`/`-wal`/`-shm`；跨进程时还需 advisory bus 让对端退役连接、以及 Knowledge MCP 子进程的生命周期配合。附件不需要这套，是因为字节只被 intake 瞬态持有。
- `channels/<platform>/<userID>/` 是**渠道用户的独立会话根**：`internal/serve/channels/dispatcher.go:3122-3125` 给出该路径，`internal/session/session.go:1385-1405` 的 `resolveDBPath` 明确把"channels 路径下、sessions.db 与句柄并列"当作一种布局权威，`session.go:495-500` 只为渠道目录写句柄文件。里面是另一个 `sessions.db` 加 `<时间戳>_<id>.db` 会话数据——删它等于删某个微信/飞书用户的历史，而且这里不存在可当年龄下限的保留期语义。

## 3. 对本批实现的影响：无

真正因重置而不可寻址的只有 `artifacts/`，而附二/三/四的回收实现从一开始就只针对它（16 位 hex 目录名、只认 `content`/`.incoming-*`、引用集只取 `session_attachments`、fail-closed、保留期+24h 年龄下限）。若当初把这两类也纳入"按 sessions.db 行集判定引用"，反而会删掉活着的知识库索引与渠道会话——本勘误同时排除了一个潜在事故。
