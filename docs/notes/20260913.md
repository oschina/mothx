## 1. 分模块审核记录

### 1.1 公共 SDK 边界: `agent/`、`bootstrap/`、`example/`

**结论: 架构声明与实现不一致(中等)**。

- `agent/types.go`、`agent/builder.go`、`agent/external_tool.go`、`agent/provider.go`、`agent/image_coordinates.go` 类型与构造器设计干净,唯一终止语义 `TaskStatus`/`EventRunFinished` 定义明确。
- **偏差 1**: AGENTS.md 声明 "Public packages must not import `internal/`; implementation wiring belongs in `bootstrap/`",但:
  - `agent/builder.go:7` import `mothx/internal/platform`(用于默认 `SessionDir()`)
  - `agent/provider_bridge.go` import `mothx/internal/config` + `mothx/internal/provider`,并在 `init()` 里 `SetResolveProviderFunc`,同时 blank-import 三个 provider 子包
  - `example/custom_provider/main.go`、`example/simple_agent/main.go` 也直接 import internal 包
- **偏差 2**: `bootstrap/bootstrap.go` 注释声称外部模块必须 blank-import bootstrap 才能启用 `NewBuilder().Build()` / `WithProviderByName`,但 `agent/provider_bridge.go` 的 `init()` 已经自我完成注册——bootstrap 对 provider 解析已是冗余的第二次注册。文档(注释)与实现脱节,且 `agent` 包本身 import internal 的事实使 "公共包不依赖 internal" 的声明不成立。
- **不成立,但无功能缺陷**: private 的全局函数指针 `buildInternal` / `resolveProviderFunc` 仅 init 期赋值,无并发写风险; `Build()` 在 `buildInternal == nil` 时会静默返回错误(外部用户跳过 bootstrap 时),行为可接受但错误信息不提示需要 import bootstrap。
- **守卫缺口**: `internal/architecture` 的动态守卫只拦截 `database/sql`、`bun`、`agent.New`、`session.Run 持久化/租约/投递`等方向,不检查 `agent/` 反向依赖 internal——所以上述偏差不会被 CI 捕获。

## 1. 逐项发现与修复方案

### F1 [Blocker] `ShutdownContext` 泄漏 `transitionMu`

**现象/触发**: run 正在收尾(或 agent 尚未绑定)时并发 `ShutdownContext`/`session/close`/进程退出。第一次 `r.Active()` 采样为 active, 但在拿到 `transitionMu` 之前 run 已被其它路径终态化, 于是走到这个 return:

```go
if !hasRunner {
    r.transitionMu.Lock()
    r.mu.Lock()
    if !r.activeLocked(runID) {
        r.mu.Unlock()
        return nil        // ← transitionMu 未解锁
    }
```

这是包内唯一手动管理 `transitionMu` 的代码块, 同块其它 return 均显式解锁(`:605/610/615/619`)。

**影响**: 该 `ExecutionRuntime` 实例的 `Begin`(`execution.go:169`)、`FinishDurable`(`execution_persistence.go:456`)、`CancelDurable`(`:429`)、`WaitForApproval`、后续 `Shutdown` 全部永久阻塞 → 该会话新 prompt 永不开始、终态行永不写入、ACP 请求永不返回。进程级、不可自愈。

**修复(方案A, 最小)**: 在 `:601` 的 return 前补 `r.transitionMu.Unlock()`(或整块改 `defer`, 但该函数其余分支是显式解锁风格, 最小 diff 优先)。
**验证**: 新增并发回归用例——"run 终态化与 `ShutdownContext` 竞态后, `Begin` + `FinishDurable` 仍能完成、`Wait` 不超时"; 现有 `go test ./internal/agentruntime/...` 必须全绿。

---

### F2 [High] 租约心跳: 2s 重试预算 + 过期即不可续约

**证据链**:
- 常量: `runtimeLeaseTTL = 15s`、`runtimeHeartbeatEvery = 3s`、`runtimeHeartbeatRetry = 2s`(`session/runtime_lock.go:20-22`);
- SQLite `busy_timeout(10000)`(`db/db.go:225`)——一次被写锁挡住最长可阻塞 10s, 已远超 2s 重试预算;
- `Renew` 的 WHERE 含 `expires_at > now`(`dao/runtime_lease.go:81`)→ 租约一旦过期, 本进程**永远续不回来**; 下一次心跳返回 0 → `markRuntimeLeaseLost` → `watchLeaseLost` 立即 `Cancel()` + 内存按 failed 收尾(`execution.go:205-231`), durable 行留非终态。

**触发**: 笔记本休眠唤醒、SQLite 长写事务(知识库重建/批量写)、VM 或调试器暂停、任意 >15s 的进程停顿。TUI 侧没有周期性 RecoveryCoordinator, 行会一直非终态, 直到下次提交/重启被 admission 恢复成 failed——用户观感就是"干到一半被打断, 且被记为失败"。

**修复(建议两步, 可分开评估)**:
1. **放宽续约条件(低风险, 推荐先做)**: 去掉 `Renew` WHERE 里的 `expires_at > now`, 只用 `owner/epoch/token + state='active'` 做 fencing。安全性已核对: 抢占方走 `Acquire` 的 `epoch = previousEpoch AND (state != 'active' OR expires_at <= now)` CAS(`dao/runtime_lease.go:58-68`), 抢占必然改写 owner+epoch, 被抢者的下一次 `Renew` 会因 epoch 不匹配失败——所以"续自己的旧行"不会产生双主。这样"没人抢占时短暂停顿"不再自杀。
2. **对齐预算**: 把 `runtimeHeartbeatRetry` 提到与 `busy_timeout` 同量级(或"重试到 `runtimeLeaseTTL` 前 X 秒"), 避免一次阻塞调用就判定失租。
3. (可选, 需讨论)**失租后主动收敛**: 目前靠"下次 admission / 其它进程的 coordinator"; 可让失租路径触发一次本地恢复扫描(以 recovery 租约终态化), 避免非终态行长期悬挂。注意 TUI-only 进程没有 coordinator, 这一条对 TUI 价值最大。

**验证**: 现有 `internal/session` 租约测试 + 新增"停顿 > TTL 但无抢占 → 续约成功、run 不中断"与"被抢占 → 旧进程失租"两个方向性用例。

### F3 [High] approval 决策 ID 跨 agent 冲突 → 子 agent 永久阻塞

**证据链**:
- ID 由每个 Agent 实例自增生成: `approvalID := fmt.Sprintf("approval-%d", a.approvalCounter)`(`agent/agent_approval.go:117-118`; question 同理 `:162`);
- 子 agent 的审批事件确实会转发到 TUI, 带 `AgentID` 但 `ApprovalID` 保持自己的 `approval-1`(`agent/subagent.go:142-150`, `:406-415`);
- TUI 用 `event.ApprovalID` 注册决策(`tui/agent_events.go:150`), 而 `DecisionService.Register` 对"已 pending"和"已 resolved"都返回错误(`agentruntime/decision.go:120-125`);
- 去重函数只在 **ID + AgentID 同时相同**时才拦截(`tui/approval.go:238-251`), 所以跨 agent 的 ID 冲突不被拦截, 直接走:

```go
if err := a.run.registerDecision(event.ApprovalID, agentruntime.DecisionApproval); err != nil {
    a.addCommandError(fmt.Sprintf("duplicate approval request: %v", err))
    return a.listenAgentEvents()      // 请求被丢弃: 不显示、不入队、不 Bind
}
```

**影响**: 该审批永不展示, 而 `RequestToolApproval` 只等 `responseCh`/`a.abort`(F4), 于是子 agent 卡住 → 父 agent 的工具(如 `subagent_wait`/delegate)永不返回 → 整条 run 卡到用户按 Esc(并丢掉全部进行中工作)。触发条件: 非 yolo 模式 + 专家团/子 agent(serve 侧也有同样的 ID 复用, 只是 `Register` 失败被 `DebugLogf` 吞掉, 表现为审批不注册)。

**修复(方案A, 推荐)**: 让 ID 天然全局唯一, 一处修全部前端:
```go
approvalID := fmt.Sprintf("approval-%s-%d", a.id, a.approvalCounter)
questionID := fmt.Sprintf("question-%s-%d", a.id, a.questionCounter)
```
已核对爆炸半径: 无代码解析该格式(仅 `agent_approval.go` 生成), ACP/serve 各自用自己的 ID; 测试里硬编码的 `"approval-1"` 都是手工构造/传入的不透明字符串, 不受影响, 仅 `internal/agent/agent_approval_test.go`、`coverage_test.go` 需改用事件里返回的真实 ID。
**方案B(兜底, 可与 A 并存)**: TUI 侧注册失败时改为"入队等待"而不是丢弃(参考 `hasPendingApproval` 的去重语义扩展为"同 ID 不同 agent 也排队"), 保证即使 ID 冲突也不会丢请求。

### F4 [High] 审批等待不吃 ctx

**证据**: `resolveToolApproval` 不接收 ctx(`agent/agent.go:2416-2426`), `RequestToolApproval` 只 select `responseCh`/`a.abort`(`agent_approval.go:133-141`); 与之相邻的 `RequestQuestion` 有 `ctx.Done()` 分支(`:175-188`)——不对称说明是遗漏。工具执行 ctx 本身是有超时的(`agent.go:2275` 起, 5min `defaultToolExecutionTimeout`)。

**影响**: run 被"纯 ctx 取消"(失租、外部停止)或子 agent 的父 run ctx 取消时, 审批等待不返回 → `BoundedParallel` 的 `wg.Wait()`(`parallel.go:33-50`)无界 → 不产生 `EventRunFinished` → durable 行停在 `cancelling`、会话租约被一直持有。F3 的卡死也是靠这条才无法自愈。

### F5 [High/Med] loop 事件发送不看取消 + TUI 中断后停止消费

**证据**:
- `loop()` 内所有事件都是裸 `ch <- Event{...}` 直发 100 缓冲通道(`agent.go:1303/1304/1418/1421/...`), ctx-aware 的 `eventSink.send`(`agent.go:84-98`)只用于子 agent 转发;
- TUI Esc: `abortPendingRequest` 里 `a.eventCh = nil`(`tui/app.go:1680`), 且 `agentEventMsg` 对通道不匹配的消息直接 `return a, nil` 且**不再重新监听**(`app.go:1220-1222`); 读取端一次只取一个事件(`tui/events.go:35-42`)。

**影响**: 若 Esc 时刻缓冲已满, agent goroutine 永久停在发送上, 到不了循环顶部的取消检查, 终态事件/收尾永不发生, 并泄漏 goroutine 与未闭合的 turn。TUI 侧因为已自行终态化并释放租约, 主要表现为"卡住不动/资源泄漏"。

**修复(建议双管)**:
- **主修(agent 侧, 对全部前端生效)**: `loop`/`emitRunFinished`/压缩等发送点统一改走 `sink.send(ctx, ev)` 或等价 ctx-guard 发送; 注意 `EventAgentStart`(`:1246`)在 `runCtx` 创建之前, 需要调整顺序或用外层 ctx。
- **辅修(TUI 侧, 便宜且能立刻消除隐患)**: 中止时不要停止消费——保留一个后台 goroutine `for range oldCh {}` 把旧流排空(drain), 或保留监听但用 `runTerminalHandled` 式标志忽略 UI 更新。这样任何"旧流仍在生产"的情况都不会反向阻塞 agent。

**验证**: 新增"缓冲填满时取消 → loop 在 N 秒内返回且发出唯一终态事件"的用例。

### F6 [Med] TUI 从不持久化决策结果

**证据**: `tuiRun.resolveDecision`(`run.go:70-80`)是全仓库唯一会写 `decision_resolved` 的 TUI 路径, 但生产代码无调用者(仅 `run_test.go` 调); `finishApproval` 直接 `handlePendingApprovalResponse` → `agent.HandleApprovalResponse`(`approval.go:186-218`), 绕过 DecisionService; 问题回答路径同理(`input.go:351-373` 直接调 `a.agent.HandleQuestionResponse`)。已有绑定回调(`agent_events.go:154-165`)专门为"走服务解析"而写, 但从未被触发。而 `resolveWith` 会先调 resolver 再调 commit(`decision.go:157-230`), 也就是说改用 `ResolveWith` 是现成设计。

### F7 [Med] Esc 后排队 prompt 不恢复

### F13 [Low] Ctrl+C 退出: 有 Runtime Shutdown, 但 TUI 不做 run 终态化

**证据(修正此前"完全不清理"的判断)**: TUI 主流程 `defer runtime.cleanup()`(`cmd/mothx/main.go:392`), cleanup 内含 5s 有界的 `sharedRuntime.Shutdown`(`:671-679`)。但 `tea.KeyCtrlC → tea.Quit`(`tui/app.go:1067`)不会调用 `run.cancel()/finish(...)`, 而 `shutdownLoopOwned` 在"agent loop 已绑定"时只请求取消、终态由 loop owner(即 TUI)写入——owner 已随进程退出, 于是 5s 等待超时, durable 行留非终态, 之后由恢复路径按 **failed**(而不是用户本意的 cancelled)收敛。

## 1. 自查中发现并当场修掉的 4 处问题

1. **重复实现(死代码)**: F6 之后 `App.resolveApprovalDecision`/`resolveQuestionAnswer` 直接调用 `run.decisions.ResolveWith`, 而 `tuiRun.resolveDecision`(同语义、带落盘 commit)变成了只有测试在用的死代码。已改为两个 App 辅助函数都委托 `run.resolveDecision`, 消除重复; 顺带把 `resolveApprovalDecision` 冗余的 `approvalID` 参数去掉。
2. **成员问题的等待投影缺 question_id**: `subagent_wait` 的 `pending` 条目只有 member/status/display_name, 只看该投影的 lead 看到 `status: question` 却无法回答。已补 `question_id`(omitempty) 字段。
3. **delivery 重开不级联**: 依赖失败被 `PropagateDependencyFailures` 标记为 `dependency_failed` 的操作(例如 caption 失败导致附件永久 failed)不会随依赖一起重开——重试后回复仍不完整。已新增 `ReopenDependentFailures` 并在 `ReopenFailedDeliveryOperation` 的同一事务内级联重开(claim 路径仍会拦住依赖未完成的行, 所以提前重开是收敛的)。新增用例 `TestReopenFailedDeliveryOperationRecoversDependentFailures`。
4. **过时注释**: `retireEventStream` 与 serve `run_executor` 的注释仍写"Agent loop 的发送不是 ctx-aware"; F5 主修后实际只剩**终态事件**(无条件发送)可能阻塞, 已按现状改写注释。

# 附十: L1 修复 —— 多进程 SQLITE_BUSY 抖动(2026-09-13) —— **L1 已完成**

- **提交**: `f4692ef fix: retry transient SQLITE_BUSY transaction begins`(核心改动已提交);工作区仍有本轮补充的 `internal/db/busy_test.go`(策略与 `RunInTx` 语义用例)与 `internal/db/db.go` 里 `_txlock` 的说明注释待提交。

- **问题(L1)**: `internal/session::TestSQLiteManyProcessesWriteDistinctSessions`(8 进程 × 64 消息 + 16 次用量写入, 共享一个 sessions.db)长期抖动, 干净 HEAD 亦失败。
- **复现与根因**: 复现 3/3 失败, 失败点是 `database is locked (5) (SQLITE_BUSY)`, 分别出现在 `db.Begin()`(写会话条目 / 初始化 schema)与 `RunInTx`(RecordUsage)上。
  - DSN 设了 `_txlock=immediate`(internal/db), 于是每个非只读事务都用 `BEGIN IMMEDIATE` 先抢单写锁 —— 这正是避免"延迟事务读→写升级"立即 BUSY 的手段 —— 但单次 BEGIN 的最长等待只有 `busy_timeout(10s)`。
  - `synchronous(FULL)` 在 WAL 下每次提交都 fsync; 本机 `/tmp` 在 **btrfs** 上(单 helper 32 条消息≈6.9s, 即 ~50–150ms/次提交), 768 次写事务串行时, 某个进程的 BEGIN 等待会超过 10s → 直接返回 SQLITE_BUSY。
- **修复**: 把"写者争用是暂时的"这一判断落到事务开启边界, 且**单点定义在 DSN 的属主**(`internal/db`):
  - `internal/db/busy.go`: 只有 SQLITE_BUSY(5)/SQLITE_LOCKED(6) 才重试; 总预算 `busyRetryBudget = 90s`(写者排队, 预算必须覆盖排队长度而不是单次 busy_timeout), 退避 200ms→2s, **ctx deadline 优先**(带超时的调用方不会被拖满预算); 非临时错误立刻返回原始错误。
  - 导出 `db.BeginTx`(bun)、`db.BeginSQLTx`(raw `*sql.DB`, 供 schema/迁移)、`db.RunInTx`(镜像 bun 语义: 成功提交、错误/panic 回滚)。
  - `internal/dao/database.go` 的 `Begin`/`BeginTx`/`RunInTx` 全部改走上述助手(bun 自带的 `RunInTx` 之前绕过重试, 是 RecordUsage 失败的原因); `internal/dao/bindings.go` 的 4 处直接 `d.db.RunInTx` 现在经由 DAO 包装(自动获得重试); `internal/db.Write` 用自己的 `RunInTx`; `internal/session/schema.go` 的建表与逐条迁移改用 `db.BeginSQLTx`/`busyRetryDatabase`。
- **用例**: `internal/db/busy_test.go` —— 重试策略(临时重试/永久立刻失败/包装错误识别/ctx 超时优先)与手写 `RunInTx` 的提交/回滚/panic 语义; 另用既有 `TestSQLiteManyProcessesWriteDistinctSessions` 作为端到端验证。
- **验证**:
  - 目标压测: 修复后 **5/5 通过**(55–79s; 修复前 3/3 失败)。
  - `./internal/db/ ./internal/dao/ ./internal/architecture/` ✅。

- **定位**: 另一个负载敏感用例的**名字其实在附三 §4 的验证小节里**: `internal/agentruntime::TestOldOwnerIsFencedBeforeSideEffectAfterCrossProcessTakeover`(附九 L2 写成"未点名"是我的遗漏)。
- **复现与根因**: 隔离运行 5/5 通过(1.2–2.5s)、并发负载 10 次仍未复现; 改用确定性证明 —— 在 `expireRuntimeLease` 与 `RecoverOrphanedSessionRun` 之间插入 4s(> `runtimeHeartbeatEvery` 3s), 立即复现: 恢复结果为 `Skipped`(而非 `Failed`), 用例断言失败。
  - 根因是**用例假设"过期 → 接管"窗口短于心跳周期**: 旧 owner 仍在心跳, 而 `RuntimeLeaseDAO.Renew` 按附二 F2 的有意语义**不带** `expires_at > now`, 会把自己刚被置为过期的行续回来(只有 epoch 被抢占才不可续)。机器一慢/压力一大, 恢复就会如实拒绝接管一个"看起来仍有效"的租约 —— 这是**产品的正确行为**, 不是缺陷。
  - 另一处负载敏感点是 setup: 旧 owner 进程要在 5s 内完成 exec + 迁移 + admission + BeginDurable; 慢盘/高负载下会先在 setup 失败, 与不变量无关。
- **修复**(仅测试, `internal/agentruntime/process_integration_test.go`):
  - 新增 `takeoverExpiredRun(...)`: 每次"过期 + 接管"成对重试(25ms 间隔, 30s 预算)直到接管成功, 超时给出明确诊断(旧 owner 一直在续自己的过期行)。不变量未被削弱: 恢复必须在观察到有效租约时拒绝接管。
