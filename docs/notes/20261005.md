## 逐项发现

### F1 [已修,中] 管理面网络型 handler 同步阻塞 NDJSON 读循环(head-of-line blocking)

- **位置**: `acp.go` `Run()` 分发循环 → `handleManageRequest`(manage.go)全部同步执行
- **现象**: `providers/test`(≤5s)、`providers/discover`(≤30s)、skillhub `categories/official/search/detail`(每个 HTTP ≤20s,`skillhub.defaultRequestTimeout`)在读循环线程内联执行。阻塞期间所有入站消息停摆——包括反向 `session/request_permission` 的客户端应答(`deliverResponse` 在同一循环)、`$/cancel_request`、`session/cancel`。Desktop 在 Run 等待审批时测试 provider 或浏览 SkillHub,Run 卡死数秒至半分钟,期间取消不可达。有超时兜底,非永久死锁,属可用性缺陷。
- **修复**: 分发点新增 `manageAsyncMethods` 白名单(上述 6 个只读网络方法),命中则 `go srv.handleManageRequest(req)`;其余 manage 方法维持同步。
- **并发安全依据**(逐一核查): 白名单 handler 只经 `manageSettings()`(每次 `config.LoadSettings()` 新读盘,不触碰 `s.settings` 可变字段)与 `sessionRuntime()`(持 `s.mu`)取状态,读 `rt.runtime.WorkDir`(创建后只读),不变更任何 server/session 状态;响应写入经 `wmu` 串行。变更型 handler(`settings/patch`、`providers/save`、skillhub `install/activate/uninstall` 等)保持同步,维持 FIFO 与 `refreshProviderCatalog` 依赖的单写者不变式。白名单的准入条件写进了 `manageAsyncMethods` 的文档注释。
- **单测兼容**: 门放在读循环分发点而非 `handleManageRequest` 内部——`acp_manage_test.go` 的 `callManageFixture` 直接同步调用 `handleManageRequest` 并立即读缓冲响应,行为不变。
- **回归测试**: 新增进程级 `TestACPStdioProcessManageNetworkDoesNotBlockTransport`——httptest 挂起 `providers/test` 的 ping 响应,期间发送同步 `settings/get`,断言 id 3 应答先于 id 2 到达,再放行并断言 probe 成功。修复前该场景下首个应答只能是被阻塞的 id 2(或 5s 超时错误),测试具有判别力。

### F2 [随 F1 一并解决] server 状态的隐式单线程不变式

- **位置**: `refreshProviderCatalog`(acp.go:1423)无锁改写 `s.providers/s.p/s.m/s.settings.*`
- **现象**: 正确性依赖「所有 handler 在读循环线程串行执行」这一未写明不变式,导致 F1 不能粗暴地 `go handleManageRequest(全部)`。
- **处理**: 本轮采用最小白名单方案(只并行化经核查无状态变更的 6 个方法),不变式对变更型 handler 依然成立;彻底的「管理面串行 worker + catalog 状态加锁」方案记录为后续选项,不在本轮扩大 diff。

### F3 [已修,低] 锁序约定未文档化

- **现象**: `s.mu → rt.cancelMu` 单向锁序(如 `handleCancelRequest` 持 `s.mu` 遍历 sessions 逐个取 `rt.cancelMu`)经 grep 核查无反向嵌套,但无注释钉死。
- **修复**: `sessionRuntime.cancelMu` 字段补锁序约定注释:持 `cancelMu` 时不得取 `s.mu`。
