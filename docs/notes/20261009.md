## 1. #2 ACP 取消可达性（`internal/acp`）

### 问题
`Run` 的读循环串行处理所有方法。`session/new|load|resume|fork` 会在读循环内同步执行 `openSessionRuntime`（MCP 连接、Registry/Skill 装配、replay），期间 `$/cancel_request` 与客户端对反向 approval/question 的响应都进不来，用户点取消无效。

### 变更
- 新增 `internal/acp/session_ops.go`：
  - `sessionOpLanes`：按 session 串行的异步车道（同 key FIFO、跨 key 并发、空闲自动退休；nil 车道内联执行）。
  - `server.dispatchSessionOp`（总是离开读循环）、`server.runSessionOp`（车道忙才排队，否则保持同步）、`sessionOpKey`（仅用于选车道，绝不作授权）。
- `internal/acp/acp.go`：
  - 把读循环的 `switch req.Method` 抽成 `server.dispatchRequest`，session 相关方法按 §路由表分派。
  - `server` 新增 `ops *sessionOpLanes`；`Run` 初始化；`shutdownAllSessionRuntimes` 先 `ops.shutdown()`（停止收新任务并等待在途任务）再拆 runtime。

### 路由表（关键语义）
- 始终异步（长耗时/需与之后操作保序）：`session/new`（唯一 key，并发放行）、`session/load`、`session/resume`、`session/fork`、`session/close`、`mothx/session/delete`、`session/delete`。
- 条件异步（车道空闲时保持原来的同步路径，忙时排队）：`session/prompt`、`session/set_config_option`、`session/set_mode`、`mothx/session/setTitle`、`setWorkDir`、`setMeta`、`mothx/session/history`。
- 始终同步（修复目标）：`session/cancel`、`$/cancel_request`；以及 `initialize`、`mothx/doctor`、`session/list`、`projects/*`、`worktree/*`、`attachment/*`、`mothx/manage/*`（后者沿用既有 `manageAsyncMethods` 异步规则）。

### 行为影响
- `load/new/fork` 期间的 `$ /cancel_request` 与反向 decision 响应恢复可达（核心修复）。
- 常见（无争用）路径不变：会话已加载时 `session/prompt` 仍同步派发，因此“prompt 紧接 cancel”的既有顺序不变。
- 同一 session 的生命周期操作与 prompt 现在由车道保证 FIFO；不同 session 仍并发。
- 错误分支：车道已 draining 时，`dispatchSessionOp` 回写 `-32000 server is shutting down`（transport 即将关闭，best-effort）。

### 测试
`internal/acp/session_ops_test.go`：
- `TestSessionOpLanesSerializesPerKeyAndRunsKeysConcurrently`（同 key FIFO、跨 key 并发）
- `TestSessionOpLanesBusyTracksRunningAndQueued`、`TestSessionOpLanesShutdownDrainsAndRejects`、`TestSessionOpKeyExtractsSessionID`、`TestRunSessionOpSerializesBehindInFlightLifecycleWork`、`TestDispatchSessionOpReportsShutdown`
- `TestDispatchRequestKeepsCancelReachableDuringSlowLoad`（读循环级回归：慢 load 占车道时 `session/load` 立即返回、`session/cancel` 仍被作答）

### 回滚点
删除 `session_ops.go`/`session_ops_test.go`，还原 `acp.go`（`dispatchRequest` 内联回读循环、去掉 `ops` 字段/初始化/`shutdown` 调用）。

## 2. #3 `maxConcurrentRequests` 一致性（`internal/serve/openaiapi`）

### 问题
`runSlots` 只在 chat-completions 使用，run-submit / 外部 Responses-background 不走它，因此 `maxConcurrentRequests` 不是全局 run 上限。方案 `webui-multi-session-streaming-proposal.md` §10.5 已明确它应“真正限制 Agent Run 数”。

### 变更
- 新增 `internal/serve/openaiapi/run_slots.go`：`acquireRunSlot()`（idempotent release；`runSlots==nil` 时 no-op）与 `chainReleases()`。
- `handler_chat.go`：改用 helper（语义不变）。
- `handler_run_submit.go`：admission 后立即取槽，失败即释放 lease 并 429 `concurrency_limit_reached`；槽折进 `runtimeRelease`，所有既有早退分支自动一并释放，槽在 run 终态释放。
- `background_external.go`（外部 Responses-background 提交）：同样处理。

### 行为影响
- **默认（`MaxConcurrentReqs==0`）行为完全不变**（`runSlots==nil` → no-op）。
- 仅在显式配置上限时，run-submit / 外部 responses-background 提交也会在超限时收到 429（与 chat 一致），超限不留下 durable run、不持有 lease。
- 明确范围（未改，避免越界）：channel 本地执行路径与 ESM 走各自 admission/队列，不计入此槽。

### 测试
`handler_run_submit_test.go` 新增 `TestSubmitRunRejectsWhenConcurrencyLimitReached`（429 + provider 未执行 + 无 active durable run）；既有 `TestChatHandlerRejectsWhenConcurrencyLimitReached` 继续通过。

### 回滚点
删除 `run_slots.go`，还原三处入口；或仅回滚 `handler_run_submit.go`/`background_external.go` 保留 chat 现状。

## 3. #4 SessionPool 身份唯一性（`internal/serve/openaiapi`）

### 问题/核实
`SessionPool` 以 `workDir\x00id` 为键，`GetForWorkDir("")` 扫描到重复 ID 返回 nil。核实结论：`sessions.id` 是主键（`internal/session/schema.go:14`），ID 在 session 目录内全局唯一；`getOrCreateSession` 对同 ID 异 workDir 显式报错（`handler_chat.go:1332`）。因此重复 ID 分支不可达，是 fail-safe 而非活 bug。

### 变更（无行为变更）
- `session_mgr.go`：在 `GetForWorkDir` 注释说明该不变量与 fail-safe 语义。
- 新增 `session_pool_identity_test.go`：`TestGetOrCreateSessionKeepsOneIdentityPerSessionID`（同 ID 唯一实例、异 workDir 被拒、同 ID 同 workDir 复用同一实例）。

### 回滚点
纯注释/测试，可单独 revert。

## 6. #6 channel 排队反馈（`internal/serve/channels`）

### 问题
`HandleDelivery` 在 `Wait:true` 排队时只发一次“排队中”提示，之后静默等待。

### 变更
- `dispatcher.go`：新增 `awaitChannelAdmission`，在等待期间每 `channelQueueNoticeEvery`（30s，可测变量）重发“仍在排队”进度；admission 判定仍由 Runtime 拥有，未新增超时/所有权语义。

### 行为影响
- 排队超过 30s 时新增可见进度提示（新的用户可见文案）；未改变等待/取消语义（仍受 `ctx` 约束）。

### 测试
`queue_notice_test.go`：`TestAwaitChannelAdmissionSendsQueueNoticesWhileWaiting`（短间隔+占位租约验证通知发送与释放后返回）。

### 回滚点

## 7. 基线跑批（服务 #1 决策）

- 扩展 `internal/session/write_pressure_test.go`：形状 A/B helper 与形状 C 额外上报 `beginP50/P99Us`、`ckptAttempts/Failures`、`walBytes`、`poolMaxOpen`、`poolWaitCount`、`poolWaitMs`。

## 11. 自审/核对（2026-10-09）

对全部改动做逐文件 diff 核对，并与 AGENTS.md 不变式、本文档声称的行为逐条对照。

### 已确认正确
- `internal/acp`：读循环的 `initialize` 门控与 response 分发保持不变，仅 `switch` 抽为 `dispatchRequest`；原 30 个方法分支全部保留（`mothx/session/delete` 与 `session/delete` 合并为一例）；车道 `drain` 在同一把 `mu` 下完成“判空/删除 running”，无丢唤醒；`shutdown` 先拒新任务再 `wg.Wait()`；nil 车道/`ops==nil` 均内联执行，直接调用 handler 的测试语义不变。
- `internal/serve/openaiapi`：`acquireRunSlot` release 幂等（`sync.Once`）；`chainReleases` 只被组合后的 `runtimeRelease` 使用；`handler_run_submit`/`background_external` 中“取槽失败”分支是重组前唯一的 `runtimeRelease()` 调用点，不会释放未获取的槽；之和后所有早退分支与后台 goroutine 都释放两者。默认 `MaxConcurrentReqs==0` 时 `runSlots==nil`，行为不变。
- `internal/db`：`BeginWaitQuantiles`/`beginWaitBucket` 为纯函数且直方图桶上界以常量数组声明（`[len(beginWaitBuckets)+1]atomic.Uint64` 合法）；`recordCheckpoint` 仅用 atomic，在 `state.Lock()` 内调用无锁冲突；`WalStats` 在锁内复制路径、锁外 `stat`；`PoolStats` 在锁内读 `sql.DB.Stats()`（不回调 state，无死锁）。expvar 快照由 `map[string]int64` 改为 `map[string]any` 仅新增 `wal`/`pool` 数组字段，既有整型字段保留。
- `internal/session`：`renew` 仅在“成功”与“预算耗尽”两个出口记录，`<-s.stop` 与“无租约”出口不记录（正确：非失败）；`markRuntimeLeaseLost` 在 `released` 短路之后才记围栏丢失（不会把主动释放算作丢失）。
- `internal/serve/channels`：`progress==nil` 时 `done` 无读者，`close(done)` 安全；admission 返回即 `close(done)` 停止 ticker；未引入超时/所有权语义。
- 测试：全部新增测试与既有 `internal/architecture` 守卫通过；`go build ./...`、`gofmt -l`、`go vet` 干净。

### 核对发现（已处理）
- **R1（生成文档漂移）**：`docs/en|zh/sessions.md` 更新后重新生成 `docs/llms-full*.txt`（`make docs-llms`）时，除本次的 `mothx_sqlite`/`mothx_runtime_lease` 行外，还带出了 `docs/en|zh/changelog.md` 中**早已提交但未再生成**的条目（租约总线同步、TUI 排队提示修复等，对应 `docs/notes/20261008.md` 的提交）。即仓库本已存在“changelog 与 llms-full 不同步”的漂移。已保留重新生成结果（AGENTS 要求不手改生成物、保持文档同步）；若维护者希望本次变更集不包含该无关漂移，可单独 revert `docs/llms-full*.txt` 并由后续流程统一再生成。

### 次要观察（不改，记录在案）
- N1：`internal/db` 的 `wal`/`pool` 在 `/debug/vars` 中暴露数据库文件的绝对路径。该端点默认仅 `127.0.0.1:6060`（`MOTHX`/`VIBECODING_PPROF_ADDR` 可覆盖），属本机诊断面；如需更保守可改为只报 basename。
- N2：内部心跳健康表 `leaseHeartbeatHealth.byDir` 无淘汰，键为 session 目录；生产通常单目录（1 条），理论上前提是进程内出现大量不同 session 目录才会增长。
- N3：ACP `sessionOpLanes.shutdown()` 无超时；若某个 lane 任务永久阻塞（如无超时的 MCP 连接），进程退出会等待。这与改动前“读循环被同步 handler 卡住”等价，未引入新 liveness 回归。
- N4：channel 周期提示与终态 progress 理论上有一次交错（ticker 与 `close(done)` 的 select 随机性），间隔 30s、影响仅为本机提示顺序；如需严格串行可改为显式互斥。
