# Changelog (Current Version)

This file contains the changes for the **current version only**. The full history of all versions lives in [docs/en/changelog.md](en/changelog.md).

## v1.3.103

### 💥 Breaking Changes

- **Inbound webhook support removed.** The serve inbound webhook feature (`channels.webhooks` configuration, `/webhook/*` routing, and its agent-task handler) has been removed entirely; webhook events are no longer accepted, and a `webhooks` section in existing configuration files is ignored. Use the OpenAI-compatible API or the WeChat/Feishu messaging channels instead.

### ✨ New Features

- **Cross-process session ownership is now synchronized across local processes over the lease bus**
  - The loopback UDP `SessionLeaseBus` no longer only wakes peers: notifications carry a canonical `DatabaseIdentity`, a per-origin `Seq`, and the owner PID/run, and every process keeps a global in-memory ownership view keyed by `(DatabaseIdentity, sessionId)`. Owners re-announce held leases every 10s (`ownership_snapshot`) so a lost acquire self-heals and an otherwise-silent owner stays fresh within a 30s liveness window. Receivers drop duplicate/out-of-order messages via `Seq`, mark an origin's entries uncertain on a sequence gap or an epoch conflict, and fall back to SQLite on any miss, staleness, or uncertainty — notifications never authorize admission or cancellation.
  - `agentruntime.InspectSessionExecution` now answers a fresh, remote execution lease from the synchronized cache (marked `source: "cache"`) and otherwise reads SQLite and refreshes the view; the snapshot projection is a single shared function so the two paths cannot diverge. `session.RuntimeLeaseBusMetrics()` exposes sent/send-failed/received/invalid/self-skipped/duplicate/applied/gap/uncertain counters. The wire version is 3 and the datagram limit 4096 bytes.

- **TUI queued messages are now visibly rendered while a run is active**
  - Submitting input while a run owns the session has always queued it for ordered delivery, but the queue was invisible: the input box cleared with zero feedback until the run finished. The live view now renders a styled "⏸ N queued" section below the spinner with a one-line preview per pending submission (at most 3 shown, overflow as "+N …"; multi-line input is flattened and truncated to the terminal width). The section disappears as the queue drains, and each prompt still renders its canonical "You:" transcript line when it actually starts — the indicator is pure managed-view state and never enters scrollback or session history.
  - The header is bilingual (zh/en) through the existing i18n catalog, and the new rendering is covered by focused unit tests (empty queue, counts/previews, visible cap, width bounding).

- **Cross-process session ownership is now visible in TUI and ACP before admission fails**
  - TUI and ACP previously only cancelled their own in-process runs; a session owned by another live process, an orphaned run left by a crashed owner, or a detached remote run stayed invisible until the next prompt admission rejected it. Both adapters now project the canonical Runtime snapshot (`agentruntime.InspectSessionExecution`) instead of growing local ownership state.
  - TUI: the sessions dialog and `/sessions` list render a compact ownership badge per session (running / running elsewhere / interrupted / remote / reserved / recovery failed), and activating a session prints one status line explaining a non-idle cross-process state (with the owner PID when known). A new bounded batch projector `agentruntime.InspectSessionExecutions` backs list/page views; unreadable sessions degrade to “unknown” instead of failing the listing.
  - ACP: the additive feature key `sessionExecutionState` advertises the new projection. `session/load` and `session/resume` responses carry an optional `execution` snapshot when the session is not idle, and `session/list`/`listAll` pages include `_meta.execution` for non-idle sessions only. Standard ACP semantics are unchanged; clients without the feature key can ignore the fields. Desktop-side consumption of the key is a follow-up.

- **Knowledge Base Usability Completion**
  - **Ignore rules and discovery diagnostics.** A knowledge base now accepts an `ignoreGlobs` list, merged with the fixed ignore directories and the suggested patterns read from the source root's `.gitignore`/`.mothxignore` (read-only). Every scan records a bounded discovery projection (`discovered`/`ignored`/`skipped` with per-path reasons) on the snapshot, so a file that is never indexed is explained instead of silently dropped. Files that are oversized, binary/non-UTF-8, or unreadable are marked `skipped` with a reason and are not handed to the model.
  - **Incremental diff summary.** Each rebuilt snapshot persists an `added`/`modified`/`removed`/`unchanged` projection with bounded path samples; a fully unchanged scan keeps the existing snapshot-reuse event and now carries the all-zero diff in its event data.
  - **Richer graph and query.** `knowledge_nodes` gained a `fact`/`candidate` status with `confidence`, a new `knowledge_entity_aliases` table merges a file node's basename with its path label, and Markdown links produce deterministic, locally verified `references` edges while a code file's conventional test file is linked with a deterministic `tested_by` edge and its import statements produce deterministic `imports` edges to module nodes, and a code symbol declaration is a `declares` edge rather than a generic `contains`, while a code file that references a present config file gets a deterministic `configured_by` edge, and a symbol that invokes another symbol declared in the same file gets a deterministic `calls` edge, while a document definition or an RFC 2119 requirement produces a deterministic `defines`/`requires` edge, and a document that states it supersedes another present document gets a deterministic `supersedes` edge. Queries now traverse up to two bounded hops (≤64 nodes, ≤96 edges), rank by relation weight, evidence count, and query hit, drop evidence-free candidates, and return structured `uncertainties` plus a `truncated` flag. The Indexer Agent may additionally propose candidate entities: a label that literally occurs in a cited chunk is stored as a grounded `candidate` node (never a fact), while an ungrounded one is stored evidence-free and hidden from default results. The Knowledge MCP `search_knowledge_base` result adds `relationType`/`confidence` per excerpt and projects `uncertainties`/`truncated`.
  - **Management surface.** New additive ACP methods and HTTP endpoints expose canonical index Run history (`runs/list`, `runs/get`), file-level source browsing (`sources/list`, no contents, with per-file chunk counts), index clearing (`clear`, keeps configuration and the source directory), and scheduled-state projection (`schedule`, reusing the shared Cron store for next-run, last result, and pause/resume). New capability keys `knowledgeRuns` and `knowledgeSources` gate the Desktop panels. Scheduled reindex plans are invalidated when a base's root directory is unavailable.
  - **Stable index error code.** An index pass that cannot build the configured Indexer provider/model now fails with a stable `knowledge_base_model_unavailable` code recorded on the canonical Run's structured error info and projected as `errorCode` in the run history; the ACP/HTTP management surfaces map the same code instead of a generic operation failure.
  - **Scan trigger coalescing.** A reindex trigger that arrives while a scan is already running is no longer dropped: it is coalesced into exactly one follow-up pass (the most recent trigger source wins) instead of starting a parallel scan or queueing one run per trigger. Time-window debounce is not implemented.
  - **Desktop and Web UI panels.** The Desktop knowledge panel and the Web UI knowledge view now surface index run history, source browsing, and a clear-index action, gated by the `knowledgeRuns`/`knowledgeSources` capability keys; the Web UI also exposes the schedule and ignore-glob fields.
  - **Cross-entry consistency.** The Web UI no longer forces `schedule=manual` or `thinkingLevel=none`: it reflects the persisted cadence, preserves an existing Desktop schedule on save, and sends ignore globs. An architecture guard pins the remaining legacy knowledge-context bridge (`KnowledgeCapsule`/`WithKnowledgeContext`/`knowledgeBaseRefs`) to the Runtime owner and the single ACP caller, with a documented removal condition.
  - **Quality baseline.** A controlled benchmark (`make knowledge-benchmark`) indexes a deterministic fixture and enforces documented regression thresholds for index duration, MCP query p50/p95, tool-result size, citation coverage, uncertainty coverage, and token estimate.
  - Knowledge-store schema version advances to 4; existing snapshots stay readable (added columns carry safe defaults) and are rebuilt on the next scan.

- **Context Guard Preserves Omitted Oversized Tool Outputs**
  - When a provider request would exceed the model input budget, the context guard no longer discards the oversized tool result for good: the full output is first saved to `<workDir>/.mothx/tmp/context-guard/` (private `0700`/`0600` permissions, the same staging convention as `.mothx/tmp/inputs`), and the guard tool-result message carries the file path with total line/byte counts, explicitly steering the model to page through the saved file with `read` offset/limit or search it with `grep` instead of re-running a possibly non-idempotent command (deploys, migrations, one-off scripts).
  - When the output cannot be saved (no working directory, write failure), the guard falls back to the previous omit-only wording. The staging area is pruned best-effort to the newest 50 files, and the guard status event now also surfaces the saved path.

- **Desktop Bundles the MothX Runtime and Supports Choosing the Runtime Binary**
  - **Every desktop package now ships a runnable `mothx` CLI.** The desktop release build vendors one source-built runtime per packaged architecture (macOS arm64 and x64, Windows/Linux x64) and injects the architecture-matching binary into `<resources>/app/vendor/mothx/bin/` after packing, before code signing seals the macOS bundle. Until now the macOS x64 package received the build host's arm64 runtime, so the Intel Mac client could not start its ACP runtime at all; the packaging step now verifies the bundled binary's ELF/Mach-O/PE architecture (including little-endian and fat Mach-O headers) and fails the build on a mismatch instead of shipping a broken client. Windows/Linux artifacts no longer carry a second copy of the runtime beside the app directory.
  - **Runtime binary setting.** The desktop settings (运行时 → MothX 运行时二进制) let the user switch between the bundled `mothx` executable (default) and a custom `mothx` binary path. Selection and validation live in the privileged Electron main process, the ACP runtime restarts on the switch, an unavailable custom path falls back to the bundled runtime with a visible notice, and a custom binary that fails to start rolls the selection back so the client stays usable. The `MOTHX_BINARY` environment variable remains the highest-priority development override.


### 🐛 Bug Fixes

- **Runtime lease bus listener no longer disables itself after a last-subscriber race**
  - When the final subscriber unsubscribed while the UDP listener was still binding, the listener returned before its deferred cleanup, leaving its `started`/`listening` state set and the closed socket cached, so the process silently stopped hearing cross-process ownership events until restart. The early return now resets the listener state so the next subscription rebinds.

- **Advisory UDP bus hardening: rebuild-notice scoping, receive-side coalescing, and a cheaper publish path**
  - The unauthenticated loopback lease bus accepted `database_rebuilt` notices for any path, so a forged or stale packet could make every peer process run a close/checkpoint attempt and surface a user-facing "database was replaced" warning for a file it never opened. The watcher now acts only on paths with a live cached connection in `internal/db` (new `IsCached` probe); genuinely rebuilt files are still retired exactly as before, and files this process never opened are ignored silently.
  - The wire validator no longer accepts the `renewed` type: heartbeat renewals were never published, and keeping the dead entry invited a future publisher to silently reintroduce one broadcast per session every heartbeat tick. A regression test pins both behaviors, and the Windows socket variant now documents that `SO_REUSEADDR` port hijacking can at worst degrade the advisory bus to durable SQLite polling.
  - Receive-side amplification is now bounded: serve and ACP wake handlers go through the shared `session.SessionWakeCoalescer`, which keeps at most one in-flight projection per session plus one trailing re-run (so bursts still converge on the latest durable state) instead of spawning one goroutine and one full DB re-read per datagram.
  - Publishing no longer dials a fresh UDP socket per message: one cached sender socket per broadcast address with a 200ms write deadline and a 5s dial backoff keeps lease release/run terminalization off the pathological latency path while preserving synchronous, exit-safe delivery and per-process ordering.

- **Session ownership mutation policy is now one shared path across ACP and serve**
  - Administrative mutations were forked: serve expert/capability patches reconciled orphaned runs through `agentruntime.AcquireSessionMutation`, while ACP (`withSessionMutationLease`, delete cascade) and serve session Delete/Bind/Unbind/Transfer called the raw `session.AcquireMutation(s)`. A session orphaned by a crashed owner (active run row, no live lease) therefore auto-recovered for one WebUI path but permanently failed with "session already has an active run" / `session_running` conflicts for ACP configuration changes and WebUI delete/bind/unbind/transfer.
  - These call sites now use the shared Runtime wrappers — including the new `agentruntime.AcquireSessionMutationUnlessHeld` (single owner for the "a live in-process lease is already the authority" skip, previously hand-written in both ACP and serve) and `AcquireSessionMutationGroup` (sorted, deadlock-safe multi-session acquisition with per-session orphan reconciliation) — so every entry point applies the same fenced takeover and recovery policy. The Responses-run admin paths in `responses_run_api.go` remain a documented bridge: a cancel/abandon must not trigger recovery of the very run it targets.
  - ACP prompt-admission and admin-mutation errors no longer collapse every cause into one opaque "session already has an active run"; the underlying reason (lease busy, recovery required, detached remote execution) is preserved in the wrapped error.
  - The architecture guard now rejects new adapter-level direct `session.AcquireMutation`/`AcquireMutations` calls outside the documented bridge, and regression tests cover unless-held acquisition, orphan-run recovery on delete, and group acquire/release semantics.

- **WebUI mode/capability patch no longer fails with "session runtime lease was lost" on sessions previously owned by another process**
  - Capability persistence (`SaveSessionCapabilities`) and its change events are lease-fenced writes. A session that was ever executed by another process — for example created and run in the TUI, which was then closed — keeps a released/expired `session_runtime_leases` row, so a later cold WebUI PATCH (`/api/sessions/{id}/capabilities`, `/api/sessions/{id}/runtime`) validated against a lease nobody held and always failed with `session runtime lease was lost`.
  - The idle capability-patch path now reclaims the session through the shared Runtime mutation lease (`agentruntime.AcquireSessionMutation`, the same fenced epoch-bump takeover the expert-binding patch already used), so patches succeed after a TUI/serve handoff while a live external owner still surfaces as contention. When the current process already holds the lease (an in-run patch), it remains the authority and no second acquisition is attempted.
  - Lease contention on these endpoints now maps to HTTP 409 instead of a 500, and a regression test covers patching a session whose lease was acquired and released by a previous owner.

- **ACP no longer becomes wholly unusable when the default provider lacks a key**
  - `mothx acp` used to treat an unusable default provider (missing API key, unknown provider, no usable model) as a fatal startup error: the process exited with the structured startup line, so initialize, sessions, and the entire management plane (`mothx/manage/*`) were unavailable — clients such as Desktop could not even reach the settings needed to configure a provider.
  - ACP now starts normally with a single stderr warning; management, settings, session history, skills, and knowledge bases stay available, and only execution entry points (`session/new`, `session/prompt`) return structured RPC errors carrying `code`/`fix` (for example `provider_unusable`: "default provider x has no API key"). Sessions bound to another usable provider keep working.
  - Management writes (`mothx/manage/providers/save`, `providers/delete`, and `settings/patch` touching `defaultProvider`/`defaultModel`/`providers`) now rebuild the provider catalog inside the running process, so configuring a key takes effect without restarting ACP.

- **Desktop home background no longer silently fails for large images**
  - The selected background used to be injected into the shell CSS variable `--app-user-image` as a base64 data URL, but Chromium silently drops CSS custom-property values larger than 2MiB: any wallpaper above ~1.5MB encoded past the limit and left `background-image` empty without any error, while the Home logo (rendered through `<img src>`) was unaffected — exactly the "logo works, background doesn't" symptom.
  - The renderer now converts the authorized data URL into a `blob:` object URL before injecting it into the CSS variable, keeping the injected value a short string regardless of image size, and revokes the previous object URL whenever the background is replaced or cleared. A regression test asserts the conversion and revocation path.

- **Context Compaction No Longer Fails with "max iterations (1) exceeded"**
  - Compaction summarizes the conversation through a child Agent built with `MaxIterations: 1` — exactly one LLM turn for the summary. Recovery retries inside the loop (empty-response retry, output-limit escalation and continuation, content rejection, context-overflow recovery, and Responses remote-state replay) each issued a fresh provider request without spending the logical iteration counter, so any single recovery consumed the only iteration and the whole compaction aborted with `generate summary: max iterations (1) exceeded`. Because a failed compaction leaves the oversized context in place, the error then repeated on every subsequent turn.
  - These recovery attempts no longer consume the logical iteration budget — each path keeps its own bounded retry counter (2 empty-response retries, 3 output continuations, 2 content-rejection stages), so `MaxIterations` now means "productive LLM turns" and a summarizer survives empty or truncated provider responses instead of dying. This aligns the loop with the existing transport-recovery rule and the shared principle that recovery must not consume the iteration budget.
  - The summarizer child keeps a limit of 3 as a safety margin for a stray phantom tool-call turn (its tool set stays empty), and the misleading "tool result summarization returned empty result" error was renamed to "summarization returned empty result".
  - Regression tests cover empty-response and output-limit recovery within a 1-iteration budget and the summarizer child recovering from empty provider responses.

- **Desktop Tasks Run and Switch Independently**
  - Desktop described "a task is running" with one global `promptInFlight` flag, so a second task could not be started while the first ran, the new-task composer was disabled whenever any other task ran, and clicking another task in the sidebar only answered "当前任务还在运行" until the user pressed "new task" again. Run state is now projected per session (`runningSessions`): a background task never marks the active one busy, never blocks a task switch, and never overwrites the active task's status. Reopening a session that is still running keeps showing it as running instead of freezing on the load state.
  - Streamed content is routed by a single rule — content belongs to the session that owns the transcript — so a task created while another one was streaming no longer mixes both conversations into one view, and a failure in the active session always explains itself in its own transcript instead of only moving the status dot.
  - Sending is single-flight: pressing Enter twice (or key repeat) can no longer create two sessions or send the same message twice.

- **Desktop Task Lists Never Keep a Deleted Session**
  - Deleting a task now drops it from every cached projection before the refresh, and a page load requested while an older one is still in flight is chained behind it instead of being answered from the stale response, so a deleted (or regrouped, or renamed) task cannot survive in an expanded project branch. A failed task-list refresh is now surfaced as a toast instead of silently freezing the list on old rows.
  - `session/delete` and `mothx/session/delete` are now idempotent: deleting an already removed session succeeds instead of failing with `session "…" not registered in DB`.

- **Task Provider Picker Shows Usable Providers, in Usage Order**
  - The Desktop task composer ignored the `apiKeyConfigured` flag that `mothx/manage/providers/list` already projects, so providers without an API key sat in the new-task and in-session pickers next to the ones that work. Both pickers now render only the providers the Runtime reports as configured, and a runtime that projects none of them (or an older runtime without the flag) keeps a selectable menu instead of an empty one.
  - Provider order is now one authoritative projection instead of a hardcoded vendor list: `mothx/manage/providers/list` orders providers by the default provider first, then by most recent recorded request, then by the stable catalog priority for providers that were never used, and reports `usageCount`/`lastUsedAt` next to each entry. Recency leads because a provider a person just added is also the one they just started running, while a pure request count would bury a new provider behind long-lived favourites. The Desktop picker consumes that order, and a session picker shows the same providers first as the next-task picker.

- **`mothx --continue` Continues the Session You Last Used**
  - `sessions.cwd` was compared byte-for-byte, so a session created through the Desktop directory picker — which stores the real on-disk casing — was invisible to a shell that spelled the same directory differently, and `mothx --continue` silently continued some other session. Session listings now match a working directory case-insensitively on Windows and macOS and keep exact matching on case-sensitive file systems.
  - "Most recent" meant most recently *created*: `SessionInfo.ModTime`, which every listing already treats as last used (the TUI's age column, Serve's `LastUsed`, the Desktop `updatedAt`), was filled with the creation timestamp. It now carries the newest persisted entry time, `CreatedAt` keeps the creation time separately, and the virtual session handle stays keyed by creation time, so session identity is unchanged. `--continue` therefore continues the session a person actually last worked in.
  - **New `mothx --list-sessions`.** Lists recent sessions across every working directory (ID, last used, message count, work directory, title), which is how a conversation started from Desktop, Serve, or a messaging channel can be found. `--list-sessions-limit` sets how many rows are printed (default 20) and `--list-sessions-cwd` narrows the list to one directory.

- **Documentation: Whether a ChatGPT/Codex Subscription Can Be Used in MothX**
  - New FAQ entry and configuration section: a ChatGPT Plus/Pro subscription **cannot** be pointed at MothX. It is served by Codex's internal backend (`chatgpt.com/backend-api/codex/responses`) and authenticated with a ChatGPT OAuth access token that OpenAI refreshes on its own schedule, neither of which fits MothX's provider credential model (plain value / `${ENV}` / `!command`), and routing subscription access into a third-party client is not what the subscription is sold for. The docs also explain why Codex CLI itself can send a ChatGPT login to a custom `base_url`, and give the two supported alternatives: the per-token OpenAI API (the built-in `openai` provider is already configured for the Codex model family with the Responses API and the Codex user agent), or any self-hosted/corporate gateway that speaks the OpenAI Responses API.
  - Configuration gains a "pointing MothX at a self-hosted or gateway endpoint" section covering `api: "openai-responses"` with `baseUrl`, declaring `models` explicitly, the supported credential forms, the `openai-chat` fallback, and verifying a gateway with `mothx doctor`/`mothx speedtest`.

- **`make desktop-dev` now exits completely on Ctrl+C**
  - The dev runner only closed its Vite renderer watcher when Electron happened to exit first. After Ctrl+C it had already marked itself as exiting, so that branch was skipped: the watcher stayed open and kept `npm run dev` — and the `make` process waiting on it — alive indefinitely. The watcher is now closed on every exit path, including the interrupt path, and the close is awaited before the process exits so it cannot be truncated.
  - Shutdown is an explicit, bounded state machine instead of a single `child.kill()`: the first interrupt terminates Electron and arms a 4-second grace period, a process that has not exited by then is killed, and a second interrupt skips the wait and exits at once. A spawn failure is reported the same way instead of surfacing as an unhandled `error` event. The exit code follows the 128 + signal convention (130/143/129) so `make` reports the interrupt.
  - Electron is spawned in its own process group on POSIX and terminated as a whole tree (`SIGTERM`/`SIGKILL` to the group, `taskkill /T` and `taskkill /T /F` on Windows), so the renderer/GPU/utility children no longer survive as headless background processes. `SIGHUP` (a closed terminal window) is handled like the other interrupts.

- **Desktop dev runner explains a missing display instead of showing a white window**
  - On a Linux host without a usable display (an SSH session, a stopped X server, X11 forwarding that never connected), Chromium aborts during platform initialization and dies on SIGSEGV. Because the window is frameless with a white background, the only symptom was a blank white window followed by a crash line, after waiting through a full build. `npm run dev` now checks for a display server first and exits within a second with an actionable explanation, without building anything, and recognises the same failure from Chromium's own stderr when `DISPLAY` is set but cannot be connected to — a case no environment check can predict. Chromium's original diagnostics are still printed unchanged, and the message lists the ways forward: a real desktop session, `ssh -X`, a virtual display (`Xvfb`, optionally under VNC/x11vnc), or the TUI / `mothx serve` Web UI for terminal-only work on a headless host.

- **Skill references can no longer escape the skill directory**
  - Reference paths parsed from SKILL.md content (`### Label (path) [已加载]` headers or Markdown links) were joined onto the skill directory without a containment check, so a third-party or skillhub-installed skill could auto-load arbitrary `.md`/`.txt` files from outside the skill directory (for example `../../../…`) into the system prompt. Parsed references now go through the same containment check as on-demand `skill_ref` loading; absolute paths and escaping paths are rejected.

- **File-tool path resolution now enforces a symlink fence**
  - `read`/`write`/`edit`/`insert`/`grep`/`find`/`ls` validated workspace containment lexically only, so a symlink inside the workspace pointing outside the session roots passed the check and let the unsandboxed host process read or write beyond the fence. `ResolvePath` now canonicalizes symlinks for both the target path and the session roots (including the not-yet-existing tail of new files) and re-checks containment on the canonical paths.

- **In-stream SSE error events now go through the provider retry loop**
  - A provider stream that emits an in-band error event/chunk mid-stream (Anthropic `event: error` such as `overloaded_error`, Google `error` chunks such as `UNAVAILABLE`/`RESOURCE_EXHAUSTED`, OpenAI-compatible `{"error":…}` chunks) previously terminated the run immediately — OpenAI chat streams even silently ignored error chunks and reported the truncated stream as a normal completion. These errors are now returned to the caller's retry classification: they are retried with bounded backoff while no visible output has been produced, and surface as a regular stream error otherwise. `IsRetryable` additionally matches `unavailable`, `resource_exhausted`, and `internal error` substrings.

- **Queued TUI prompts no longer fail with "lease is held by another process"**
  - When a run reached its terminal state and the fenced terminal-persistence write needed a retry, the Runtime kept the execution lease (by design) while it retried in the background; a TUI prompt queued behind that run immediately tried its admission and was rejected with `session runtime lease is held by another process` — a misleading cross-process error for a same-process drain window, and the queued input was dropped.
  - Shared execution admission now distinguishes draining from contention: a busy lease still held by the current process for an execution that already selected its terminal state makes queued successors (admission and session mutation) wait for the Runtime-owned release, so the session stays in this process and the queued input runs. A genuinely active same-process execution or another process's lease still fails fast for callers that did not opt into waiting.
